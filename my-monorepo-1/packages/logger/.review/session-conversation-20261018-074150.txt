【アシスタント】
現状の差分では、`createAppLogger` は共通の `Logger` に追加せず、`@my/logger/server` の名前付きエクスポートとして提供する設計を推奨します。指摘は2点です。

1. **[P1] 共通 `Logger` への追加で型チェックが失敗しています。**
   logger.types.ts:43
   クライアント用の `actionAdapter` も `Logger` を実装しているため、今回追加した必須メソッドがなく `TS2741` になります。サーバーの初期化責務は共通のログ出力インターフェースから分離するのが自然です。

2. **[P2] 公開したメソッドを呼ぶたびにロガーが再生成されます。**
   logger.winston.adapter.ts:13
   転送先の `createAppLogger()` は共有変数を新しいインスタンスで上書きします。初回ログ出力後や初期化処理の重複実行時にも、既存のロガー・transport を閉じずに作り直し、公開 API は `void` のため呼び出し側から旧インスタンスを解放できません。初期化用途なら `getLogger()` 経由で冪等にする必要があります。

提供窓口は、次の形が適しています。

```ts
// @my/logger/server
export default logger;

export function initializeAppLogger(): void {
    getLogger();
}
```

既存の遅延初期化で十分なら、この公開関数自体を追加する必要はありません。独立したロガーを生成するファクトリが目的なら、`createAppLogger(): Logger` として返し、共有変数の更新と切り離す設計が適切です。

`npm run typecheck --workspace=@my/logger` で上記の型エラーを確認済みです。ファイルは変更していません。

【ユーザー】
最初のgetLoggerのときに生成する現状の作りは残しつつ、将来的にinstrments.tsで生成できるように構えておきたいです

【アシスタント】
その意図なら、遅延初期化はそのまま残し、`@my/logger/server` に `initializeAppLogger(): void` を名前付きで公開する形が適しています。

```ts
// src/index.s.ts
import 'server-only';

import logger from '#logger/internal/logger.s';
import { getLogger } from '#logger/internal/logger.winston';

export default logger;

export function initializeAppLogger(): void {
    getLogger();
}
```

これで、通常は最初のログ出力時に生成し、将来 `instrumentation.ts` から初期化した場合はそのインスタンスを再利用できます。複数回呼んでも再生成されません。

今回の差分にある `Logger.createAppLogger` と `winstonAdapter.createAppLogger` の追加は取り除き、生成処理は内部に置いたままでよいです。共通の `Logger` はログ出力の責務に限定できます。

【ユーザー】
ログの実装はwinston以外にも切り替えられるようにしたいです。その際は専用のadapterを新しく作成します

【アシスタント】
その方針なら、公開窓口が直接 `getLogger()` を呼ぶ設計は避け、初期化も adapter 経由にするのが適切です。

共通の `Logger` はログ出力のみとし、サーバー用の型を追加します。

```ts
export type ServerLogger = Logger & {
    initialize(): void;
};
```

Winston adapter では、既存の遅延初期化を利用します。

```ts
export const winstonAdapter: ServerLogger = {
    initialize: () => {
        getLogger();
    },
    // 既存のログ出力メソッド
};
```

`logger.s.ts` で使用する adapter を選び、公開窓口はその選択に従います。

```ts
// index.s.ts
import 'server-only';

import logger from '#logger/internal/logger.s';

export default logger;

export function initializeAppLogger(): void {
    logger.initialize();
}
```

これなら、通常の初回ログ出力でも、将来の `instrumentation.ts` からの明示的な初期化でも、同じインスタンスを利用できます。実装を切り替える際は、新しい adapter に冪等な `initialize()` を実装し、`logger.s.ts` の選択を変更する形です。クライアント側の adapter に初期化メソッドを要求する必要もありません。

【ユーザー】
現状のlogger.winston.tsのcreateAppLoggerの戻り値をvoidにできますか

【アシスタント】
できます。ただし、現在の `getLogger()` は `createAppLogger()` の戻り値を使っているので、併せて変更します。

```ts
let logger: winston.Logger | undefined;

export const createAppLogger = (): void => {
    logger = createLogger({
        format: format.combine(timeStampFormat, logFormat),
    });
    // 既存の設定処理
    // return logger; は削除
};

export function getLogger(): winston.Logger {
    if (!logger) {
        createAppLogger();
    }
    return logger!;
}
```

ただ、現在のテストも戻り値でログ出力や `close()` を行っているため、変更が必要です。

設計としては、内部の生成関数は `winston.Logger` を返し、adapter の `initialize(): void` で戻り値を隠す形を推奨します。内部まで `void` にする必要はなく、上の非 null アサーションも避けられます。
