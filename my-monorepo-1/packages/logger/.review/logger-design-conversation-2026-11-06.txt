【回答】
確認したのは my-monorepo-1/packages/logger です。コードは変更していません。

独自の型とアダプターで Winston を隠す方針は妥当です。ただし、現在は「実装を選択するだけの層」が重複しており、
疎結合を維持したまま簡略化できます。今回の「コードを修正して差し替えられればよい」という要件なら、DI コンテナーなどを追加する必要はありません。

■ 残す価値がある部分

・Logger・ServerLogger：利用側が Winston の型や API に依存しないための契約。
・Winston アダプター：独自 API を Winston の呼び出しに変換する場所。
・Winston の生成・設定処理：設定量があるので、アダプターから分離する意味があります。
・client／server の公開入口：実行環境の違いを明確にできます。

■ 簡略化できる部分

現在、サーバー側は次の経路です。

index.s.ts
  → logger.s.ts
    → logger.s.adapter.ts
      → logger.winston.adapter.ts
        → logger.winston.ts

このうち、src/internal/server/logger.s.ts:9 は代入だけ、src/internal/server/logger.s.adapter.ts:6 は常に同じ実装を返す関数です。
クライアント側も同様です。

実装の選択場所は一つあれば十分なので、例えば次の構成で目的を満たせます。

共通の型

server/
  logger.ts                 ← 実装を選択して公開
  adapters/
    winston.adapter.ts      ← 独自 API との変換
    winston.ts              ← 生成・設定

client/
  logger.ts                 ← 実装を選択して公開
  adapters/
    server-action.adapter.ts
    server-action.ts

index.s.ts・index.c.ts は公開入口として残して構いません。差し替えるときは、
それぞれの logger.ts の import・export を変更するだけです。条件分岐のない resolve...() は不要です。

また、クライアント側の実体は「Server Actions で送信する処理」なので、名前から winston を外すと責務が明確になります。

■ ファイル数より先に整理したい点

1. クライアントの送信先が、サーバーの実装選択箇所を迂回しています。

src/internal/client/adapters/logger.winston.action.ts:9 は winstonAdapter を直接参照しています。
そのため、logger.s.adapter.ts を別実装に差し替えても、クライアント経由のログは Winston に残ります。

Server Action からも内部のサーバーロガー窓口を呼べば、サーバー実装の変更箇所を一つにできます。
現在の依存経路なら、その形で循環参照にもなりません。

2. 共通インターフェースが、実装の提供できる機能より大きくなっています。

src/internal/isomorphic/logger.types.ts:42 の Logger 型は同期・非同期の両方を要求していますが、
サーバー側の *Async とクライアント側の log・warn などは空実装です。

これは冗長さ以上に、呼べるのにログが出ないことが問題です。使わない機能は契約から外すか、
client／server で必要な型を分ける方が扱いやすいです。共通化するのは、両方が実際に保証できる部分だけで十分です。

3. 非同期 API の意味が揃っていません。

src/internal/client/adapters/logger.winston.action.adapter.ts:17 では、info が送信を await し、
infoAsync が void logInfo(...) で送信完了を待たずに終わります。さらに公開型の info は void なので、待機できる契約になっていません。

「送信完了まで待つ必要があるか」を先に決め、原則として API を一系統にするとシンプルです。
なお、Server Action の完了と、ログファイルへの書き込み完了は別の保証です。

4. 生成した Winston ロガーがキャッシュされていません。

src/internal/server/adapters/logger.winston.ts:64 の getOrCreateLogger は、
生成結果を gLogger に代入していないため、現在は呼び出すたびにロガーと transport を作ります。
initialize() で生成したインスタンスも保持されません。これは設計の簡略化とは別に、優先して直したい不具合です。

私なら、独自の型と実処理を持つアダプターは残し、単なる中継層を統合します。
そのうえで、空実装をなくし、Server Action の送信先をサーバーの共通窓口に揃えます。
この程度で、今回求めている差し替えやすさとシンプルさを両立できます。

【追加の会話：Async の意味】

ユーザー:
ログのAsync系は待機しないログ出力で、失敗判定もしません。Async無しは待機するログ、と言う位置づけです。

回答:
命名の意図を次のように理解しました。
・Async あり：ログ処理の完了を待たず、失敗も判定しない。
・Async なし：ログ処理の完了を待つ。

この前提なら、前回の「infoAsync が送信完了を待たない」という指摘は取り下げます。意図どおりの動作です。

そのうえで、残る整理点は次の3つです。

1. Async なしの公開型を Promise<void> にする。
クライアントの実装では await していますが、Logger.info() などの型は void です。呼び出し側でも await logger.info(...) する契約に揃える必要があります。内部で待機するだけでは、呼び出し側の処理は待機しません。

2. 「待機」の完了条件を決める。
現在の Server Action は logger.info() を呼ぶだけです。サーバー側も Winston にログを渡した時点で戻るため、現状で待てるのはサーバー処理の応答までです。ログファイルへの書き込み完了まで待つ意味なら、追加の実装が必要です。

3. 失敗を判定しない場合も、Promise の reject を処理する。
void logInfo(...) は戻り値を捨てますが、reject を処理するものではありません。失敗を呼び出し元に通知しない方針でも、アダプター内で .catch(() => {}) などにより吸収すると、意図が実装上も明確になります。

命名は一般的な Async の使い方とは異なるため、型のコメントにこの定義を明記すると理解しやすくなります。メソッドを二系統に分けること自体は、その使い分けが必要なら妥当です。

【追加の会話：環境ごとの使い分け】

ユーザー:
クライアントサイドロガーはAsyncで出力（待機も失敗判定もしないで投げっぱなし）、サーバーサイドロガーは同期で出力、と言うふうに整理するのはどうですか

回答:
その整理は妥当です。現在の用途なら、同期・Async のメソッドを両方用意するよりシンプルになります。

・クライアント：サーバーへ送信し、完了を待たない。失敗も呼び出し元へ通知しない。
・サーバー：その場でロギングライブラリを呼び出す。

この形なら、両方とも info・warn・error・debug などの名前にして、戻り値を void に揃えられます。*Async は不要です。共通の契約は「ログ出力を依頼する」と考えると自然です。

ただし、サーバー側の「同期」は、ファイルへの書き込み完了まで待つ意味にはしないのが現在の実装に合っています。今のコードが保証するのは、Winston のログメソッドを呼び出すところまでです。コメントも「同期出力」より「Winston にログを渡す」と書く方が正確です。

クライアント側では、投げっぱなしでも Promise の reject は内部で吸収します。例えば次の形です。

info: (message, extras) => {
    void logInfo(message, extras).catch(() => {});
},

これは呼び出し側に待機や失敗判定を要求せず、送信失敗も外へ伝えない実装です。

この方針なら、共通型から *Async を削除し、通常メソッドを各環境に合う方法で実装するだけで済みます。空実装も減り、差し替える実装が満たすべき契約も小さくなります。

【追加の会話：環境ごとに公開するメソッドを分ける案】

ユーザー:
ログを呼ぶ側が同期か非同期が意識できるように、クライアントロガーではAsync系のみを実装、サーバーサイドではAsync無しを実装、とするのはどうですか

回答:
その設計は妥当です。呼び出し側に動作の違いを明示したいなら、型も client／server で分けるのがよいです。

・ClientLogger：infoAsync・warnAsync・errorAsync・debugAsync などだけを提供する。
・ServerLogger：info・warn・error・debug などと、必要なら initialize を提供する。

共通化するのは Level・Extras などのデータ型に留めれば十分です。両者に同じ Logger 型を実装させる必要はありません。これで、未対応のメソッドを空実装で埋める必要もなくなります。

クライアント側の *Async は、今回の方針なら戻り値を void にするのが自然です。送信を開始し、Promise の失敗は内部で吸収します。Promise<void> を返すと、呼び出し側に「待機・失敗判定できる」と受け取られやすいためです。

ただし、Async は一般に「Promise を返す関数」にも使われる名前なので、型コメントに「送信完了を待たず、失敗も通知しない」と明記するとよいです。また、サーバー側も「ファイル書き込み完了まで待つ」という保証にはならない点は、区別しておく必要があります。

現在の要件では、無理に共通インターフェースに揃えるより、この分離の方がシンプルで意図も明確です。
